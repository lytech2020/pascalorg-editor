# AI 增删改问题审计与修复任务

> 审计日期：2026-07-24
> 代码基线：`4eb3ee27`
> 范围：仅评估 `pascal-ai-mcp/**` 的增删改链路；不修改 `packages/**`、`apps/**`、MCP 工具契约或根配置。
> 性质：问题盘点与修复计划，不代表下列问题已经修复。

## 1. 结论

当前系统不是“增删改都不能用”，而是同时存在以下四类问题：

1. **能力边界没有被准确表达**：单件家具删除与整房家具清空被当成同一种请求；“桌子”等含糊家具词可以通过模型解析，但执行器没有稳定语义。
2. **部分已声明支持的路径存在实现缺陷**：例如在客厅增加桌子，模型解析成功后没有产生任何场景写入，却最终被报告为“结构重建写入后失败”。
3. **写入安全与恢复语义仍有高风险缺口**：通用重试函数会自动重试 `create_room`、`place_item`、`delete_node` 等写工具；当第一次写入已经提交但响应丢失时，第二次调用可能产生重复副作用。
4. **后置验证和用户回复丢失了真正的失败原因**：目录无匹配、房间歧义、空间不足、目标不存在等不同情况最终都被压缩成 `furniture_target_not_met`，用户看不到可操作的说明，审计也不足以还原失败阶段。

因此，在内部多人试用前应当继续修改代码。优先级不是先扩充所有功能，而是：

1. 先禁止写工具自动重放；
2. 修正“是否真的写入过”的判定与错误话术；
3. 修正房间、家具目标的确定性绑定；
4. 再补家具批量删除、桌类家具放置和更完整的增删改能力。

上述主要修复都可以只改 `pascal-ai-mcp/**`，不要求修改冻结的 MCP 或 Editor 目录。

## 2. 本次现场复现

本次在同一测试场景中复现了两条请求。两次请求的模型调用均成功，但工具审计中只有读取和目录查询，没有任何场景写工具。

### 2.1 删除卧室全部家具

- 用户请求：`把洋室1的家具删除了吧`
- requestId：`021dd5d5-4292-4b45-afe8-6a004febe885`
- 实际工具：`load_scene`、`get_zones`、`get_walls`、`get_level_summary`、`get_scene`、`search_assets`
- 实际写入：无
- 场景结果：家具未删除
- 用户收到：`modification verification failed (furniture_target_not_met)`，并被告知场景可能处于部分修改状态

这里包含两个独立问题：

1. 当前 `ModifyOp` 只有 `remove_furniture(room, item)`，只能删除一个有明确家具类别的目标，没有“清空房间家具”操作；
2. 零写入失败被错误归类成了“写入后失败”。

### 2.2 在客厅增加桌子

- 用户请求：`在客厅加一个桌子吧`
- requestId：`740d7875-b4e0-43f5-bf2a-14e873fb863d`
- 实际工具：与上例相同，只有读取和目录查询
- 实际写入：无
- 场景结果：未增加桌子
- 用户收到：同样的 `furniture_target_not_met` 和结构重建失败提示

这不是合理的安全拒绝。“增加一件家具”已经被能力矩阵声明为支持，失败来自当前实现：

- Prompt 允许模型输出任意非空家具词；
- `桌子` 不属于现有家具 checklist 的稳定词汇，只有 `书桌` 等更具体类别；
- 执行器没有“含糊家具概念 → 澄清或房间语境候选”的确定性步骤；
- 即使目录能检索到桌子，所有家具也统一使用贴墙扫描，餐桌、茶几等中心型家具很容易找不到位置；
- 最终详细原因被后置验证丢弃。

## 3. 当前真实能力矩阵

现有 `eval/crud-matrix.json` 的 `supported` 粒度过粗。更准确的口径如下。

| 操作 | 当前真实状态 | 主要条件或限制 |
|---|---|---|
| 新建完整户型 | 条件支持 | 依赖模板/partition、施工与全场验证 |
| 增加房间 | 条件支持 | 实际是全方案重建；可能因面积、连通、稳定性约束在写入前安全拒绝 |
| 删除房间 | 条件支持 | 仅部分户型可局部吸收，否则全方案重建；不能承诺回滚 |
| 调整房间面积 | 条件支持 | 全方案重建；目前后置验证只检查“至少达到目标” |
| 重命名房间 | 支持 | 局部 patch，并有范围保护 |
| 增加明确类别家具 | 条件支持 | 依赖词汇、目录命中、前四候选及贴墙位置 |
| 删除一件明确家具 | 条件支持 | 多个匹配时只删除列表中的最后一个 |
| 替换一件明确家具 | 条件支持且可能部分完成 | 先删旧家具，再放新家具；后半段失败会留下部分结果 |
| 删除房间全部家具 | 不支持 | 没有批量操作契约、预览、确认或批量后置验证 |
| 移动家具到指定位置 | 安全拒绝 | 没有确定性位置契约 |
| 直接增删改门窗 | 安全拒绝 | 不在 `ModifyOp` 契约内 |
| 直接移动墙体 | 安全拒绝 | 不在 `ModifyOp` 契约内 |
| 混合修改 | 条件支持且风险较高 | 前序子操作成功、后序失败时可能形成部分修改 |
| 查询场景 | 支持 | 只读工具路径 |

文档和机器矩阵应把“契约存在”和“对任意场景都可执行”分开。`supported` 不应继续掩盖布局相关的可行性条件。

## 4. 代码链路概览

当前修改链路为：

```text
用户请求
  → modify-ops Prompt
  → parseModifyOps（只校验字段形状）
  → classifyModificationMode
  → furniture-only / local patch / plan rebuild
  → MCP 读取与写入
  → local patch scope / plan validator / completion gates
  → modification postconditions
  → 会话、审计与用户回复
```

主要问题并不集中在模型一层，而是每一层都存在信息损失：

- 解析层不知道 `家具` 是批量概念，也不知道 `桌子` 是含糊概念；
- 目标绑定层在家具直达路径中没有统一使用严格房间解析；
- 执行层把全部家具都按贴墙家具处理；
- 写入层自动重试非幂等操作；
- 后置验证层把具体失败压成一个通用 code；
- 错误处理层用过早设置的布尔值推断“已经写入”；
- 用户回复层把家具局部失败描述成结构重建失败。

## 5. P1：优先修复的问题

### P1-1 写工具会被自动重试，可能产生重复副作用

`scene-executor.ts` 的 `callWithRetry` 对所有工具统一执行最多两次。它既用于读取，也用于：

- `create_room`
- `cut_opening`
- `apply_patch`
- `add_door`
- `add_window`
- `place_item`
- `delete_node`

现有测试甚至明确验证了 `create_room` 首次抛错后自动再调用一次。

问题不在于“明确失败后再试”本身，而在于调用方无法判断第一次是否已经在 MCP 侧提交。例如：

1. `place_item` 已经创建家具；
2. 响应在传输过程中丢失；
3. AI 服务把它当成失败并再次 `place_item`；
4. 场景出现两件家具。

这与连接层已有的“写调用绝不自动重放”原则冲突。连接层不重放并不能抵消执行器自己的重试。

**建议**

- 拆成 `callReadWithRetry` 和 `callMutationOnce`；
- 只有明确只读工具允许透明重试；
- 写工具失败一律保留 `result_unknown`/`failed_recoverable` 证据，不自动重放；
- 为所有写工具增加“第一次可能提交但响应丢失”的回归测试。

### P1-2 零写入失败被误判为写入后失败

家具直达路径在调用家具执行器前就设置：

```text
session.modificationWriteStarted = true
```

随后即使只发生读取、目录无匹配、找不到合法位置，catch 仍会把它当成 destructive failure，并向用户声称场景可能已经部分修改。

现场两次失败的审计均证明没有写工具调用，但 UI 都出现了该错误。

**影响**

- 用户被错误告知场景可能损坏；
- 系统禁止自动重试，明明这类失败可以安全修正措辞后重新提交；
- 真实的目录/放置问题被掩盖；
- 失败统计把安全的零写入失败混入 `failed_recoverable`。

**建议**

用明确的副作用状态替代单一布尔值：

- `no_write`：尚未调用写工具；
- `write_attempted`：写调用已发出，结果可能未知；
- `write_confirmed`：收到成功结果并记录目标 ID/version；
- `partial_write_confirmed`：部分子操作成功，后续失败。

该状态应由统一 MCP 写调用包装器更新，不能由业务流程在调用前猜测。

### P1-3 家具房间目标可能被模糊匹配到错误房间

严格的 `resolveRoomRef` 会在同类房间超过一间时拒绝猜测，但家具直达路径直接使用模型计划，由 `furniture-modify.ts` 自己解析房间：

```text
zone id → exact name → substring name → first match
```

当场景存在 `卧室1`、`卧室2`，模型输出 `卧室` 时，substring 分支会选择数组中的第一间，而不是要求澄清。Prompt 虽要求使用房间原名，但这不是确定性安全边界。

**建议**

- 所有家具操作在执行前统一经过严格 `resolveRoomRef`；
- 执行器只接受已经绑定的 `roomId/zoneId`，不再自行做 substring 猜测；
- 多个候选必须安全拒绝并列出可选房间，不得选择第一项。

### P1-4 结构重建成功后，后续家具失败可能留下旧快照

结构修改和家具修改混合时，场景结构可能已经完成重建；如果后续家具执行或后置验证失败，会话的新 `layoutIntent/layoutPlan` 可能尚未落定。结果是：

- MCP 场景已经是新结构；
- Session 仍保存旧方案快照；
- 下一次修改基于旧快照计算，产生 drift、错误拒绝或错误重建；
- 用户只看到笼统失败，无法知道哪些子操作已经成功。

这类情况不能靠假回滚处理，因为当前没有可靠的跨系统回滚能力。

**建议**

- 每个确认成功的结构写阶段立即持久化可验证边界；
- 后序家具失败时，先重新读取并验证场景，再更新 Session 到已确认的新结构；
- 回复中列出“已完成”和“未完成”的子操作；
- 结果不明确时保持 `failed_recoverable`，禁止盲目重放。

## 6. P2：功能正确性和可用性问题

### P2-1 `ModifyOp` 无法表达批量家具删除

当前只有：

```json
{"op":"remove_furniture","room":"洋室1","item":"床"}
```

没有：

```json
{"op":"clear_room_furniture","room":"洋室1", "...policy":"..."}
```

模型只能把“删除全部家具”错误压成 `item: "家具"`，字段校验仍会通过，执行器再把“家具”当作目录关键词搜索，最终失败。

**建议**

新增显式批量操作，而不是把 `家具` 当通配符：

- 写入前列出目标 item IDs 和数量；
- 默认只处理可移动家具；
- 厨房、卫浴的必要设备和内置构件默认保留；
- 需要一次明确确认；
- 后置验证检查目标 ID 全部消失、非目标节点未变化；
- 逐件调用失败时报告精确的部分完成结果，不承诺自动回滚。

该能力可用现有 `get_level_summary` 和 `delete_node` 完成，不需要修改 MCP 契约。

### P2-2 家具词汇契约与 Prompt 不一致

Prompt 允许任意“简短通用词”，解析器只要求非空字符串；执行器的稳定跨语言匹配却依赖有限 checklist。当前稳定词汇包含 `书桌`，但不包含泛称 `桌子` 或明确的 `餐桌`/`茶几`完整类别模型。

**建议**

- 建立修改专用 furniture concept registry；
- Prompt 只能输出 registry 中的 concept key，而非任意文本；
- `桌子`这类有多个合理解释的词应结合房间和用户上下文进行澄清；
- 不要默认把客厅“桌子”静默改成书桌、餐桌或茶几；
- 目录查询词、现有家具匹配词和用户显示名都从同一 registry 派生。

### P2-3 所有家具都采用贴墙放置

`placeCandidate` 对所有家具统一调用 `findWallPlacement`。这适用于床、衣柜、书桌等靠墙家具，却不适用于：

- 餐桌
- 茶几
- 中岛
- 部分沙发组合

因此“目录有资产、房间也有空间”仍可能被错误判断为放不下，或者被放在不合理的墙边。

**建议**

为家具概念增加 placement strategy：

- `wall_aligned`
- `room_center`
- `relative_to_anchor`（例如茶几相对沙发）
- `service_wall`

第一阶段至少支持墙边与房间中心两类，并继续使用碰撞、门口净空和房间边界验证。

### P2-4 后置验证只保留通用失败码

家具执行器已经能产生较具体的 detail：

- 找不到房间；
- 目录无匹配；
- 房间内没有目标家具；
- 没有合法位置；
- 删除成功但新家具放置失败。

但 `validateModificationPostconditions` 只输出：

```text
furniture_target_not_met
```

这导致用户、日志和测试都无法区分失败原因。

**建议**

使用稳定、低敏感的结果码：

- `room_not_found`
- `ambiguous_room`
- `catalog_no_match`
- `item_not_found`
- `no_safe_position`
- `mutation_failed`
- `mutation_result_unknown`
- `replacement_partial`
- `scope_violation`

审计只保存枚举、数量和目标 ID，不保存 Prompt、原始工具响应或用户完整文本。

### P2-5 家具结果按数组位置与操作配对，容易错位

后置验证用 `furnitureIndex++` 按顺序消费执行结果。如果中间某个家具操作因同请求中房间被删除而被规划器忽略，原计划仍参与验证，但执行报告中没有对应结果，之后的家具结果会与错误的 operation index 配对。

**建议**

- 为每个 `ModifyOp` 分配稳定 `operationId`；
- 执行报告按 `operationId` 返回；
- 被忽略、拒绝、未执行的操作也必须产生明确结果；
- 后置验证按 ID 关联，不按数组位置猜测。

### P2-6 多个同类家具时“删除最后一件”的依据不可靠

当前多匹配时选择 `matches[matches.length - 1]`，文案称其为“最后放置的一件”，但代码没有读取创建时间或稳定排序字段，实际只是上游列表中的最后一项。

**建议**

- 用户未指明且存在多个匹配时，默认澄清或显示候选数量；
- 若产品决定“删除最后放置”，必须使用可靠的创建序号/时间；没有可靠字段时不得这样描述；
- 若选择按最近位置、离入口等规则，也必须明确并可测试。

### P2-7 面积后置条件把“目标值”当成“最小值”

`add_room` 和 `resize_room` 的后置验证只检查：

```text
actual >= target - 0.05
```

因此“调整到 16㎡”得到 25㎡仍可能通过该项后置条件。通用面积规范可能拦住极端值，但不能证明满足了用户的具体目标。

**建议**

- 在操作契约中区分 `exact`、`at_least`、`range`；
- “调整到 16㎡”按允许误差的双边范围验证；
- “至少 16㎡”才使用单边下限；
- Provider eval 同时覆盖偏小和明显偏大的结果。

### P2-8 混合操作缺少用户可见的逐项结果

rename、家具、结构重建可以组合在一个计划中。当前任意后序失败可能让整次请求只返回一个总失败，但前序操作可能已经成功。

**建议**

为每个 operation 记录：

- `planned`
- `not_started`
- `succeeded`
- `failed_no_write`
- `failed_recoverable`
- `skipped_dependency`

最终回复应按子操作列出结果，不把“部分成功”称为完整成功，也不把“零写入失败”称为场景可能损坏。

## 7. P3：一致性与可观测性问题

### P3-1 家具归属主要按中心点判断

家具跨越房间边界时，只要中心点落在某房间，就可能被归入该房间并成为删除目标。此问题发生概率较低，但应在批量删除前使用完整 footprint containment 或交叠比例复核。

### P3-2 审计不能还原安全的失败类别

现有审计正确地不保存工具参数值和原始响应，这一隐私边界应保留。但当前也没有记录足够的低敏感结果码，导致现场只能知道调用过 `search_assets`，无法知道是：

- 查询为空；
- 候选尺寸不合适；
- 放置碰撞；
- 模型输出了未知词；
- 执行器没有进入写阶段。

应新增枚举型 outcome，而不是扩大原始内容留存。

### P3-3 请求成功与业务修改成功容易混淆

HTTP/队列请求可能以 `succeeded` 结束，但 Session 是 `completed_with_issues`，修改并未达成。这种双层状态本身合理，但指标、内部测试报告和 UI 必须同时展示：

- 请求处理终态；
- 业务修改终态；
- 是否发生写入；
- 是否存在结果未知的副作用。

不能只按 `ai_requests.status='succeeded'` 统计修改成功率。

### P3-4 能力矩阵过度使用 `supported`

`add-room`、`remove-room`、`add-furniture`、`remove-furniture` 当前都写成无条件 `supported`，没有表达：

- 布局是否可行；
- 是否只支持单件；
- 是否要求稳定词汇；
- 是否只支持某类放置；
- 是否可能在执行前安全拒绝。

建议给机器矩阵增加 `conditions` 和 `limitations`，或者将 disposition 拆成：

- `supported_deterministic`
- `supported_conditional`
- `safe_rejection`
- `failed_recoverable`

## 8. 自动化测试缺口

当前 deterministic 测试覆盖了标准的 `书桌`、`床`、`衣柜`等 fixture，但没有覆盖真实用户最容易说出的边界请求。

至少补充以下零费用用例：

1. `在客厅加一个桌子吧`：不得进入通用失败；应澄清或成功放置明确桌类家具；
2. `把洋室1的家具都删除`：进入显式批量确认，不得把“家具”当普通 item；
3. `删除卧室的床`，但存在卧室1/卧室2：必须澄清，不得选择第一间；
4. 目录无匹配：零写入，回复 `catalog_no_match`；
5. 有目录但无合法位置：零写入，回复 `no_safe_position`；
6. `place_item` 已提交但响应丢失：绝不自动第二次调用；
7. `delete_node` 已提交但响应丢失：不得盲目重放；
8. swap 删除成功、放置失败：精确报告 partial；
9. rename 成功、家具失败：逐项报告并刷新 Session 快照；
10. 结构重建成功、家具失败：Session 与实际场景结构一致；
11. 多个同类家具：不得把无排序依据的最后元素称为“最后放置”；
12. resize 目标明显超出：双边目标验证失败；
13. local scope：所有家具操作只影响绑定房间和明确 item IDs；
14. 零写入失败：不得出现“场景可能部分修改”的提示；
15. 所有安全失败：工具审计中写调用数为 0。

Provider eval 在 deterministic 全绿后再运行，并需单独获得费用授权。优先抽查自然语言歧义，而不是只重复已有标准词 fixture。

## 10. 推荐实施顺序

```text
R1 写入安全
  → R2 目标绑定
  → R3 家具语义与放置
  → R4 批量清空
  → R5 混合修改一致性
  → R6 房间契约校准
  → R7 全量验收
```

R1 和 R2 是内部测试前的阻塞项。R3、R4 决定家具增删改是否真正可用。R5 防止部分失败污染后续会话。R6 主要校准房间结构修改的产品承诺。没有完成 R1 前，不建议通过增加更多 Prompt 规则掩盖执行层问题。

## 11. 明确不做的事

- 不修改 `packages/mcp` 来绕过 AI 侧契约问题；
- 不修改 `apps/editor` 来掩盖后端错误状态；
- 不保存模型原始回答、工具原始参数或完整场景作为排障捷径；
- 不使用 `get_scene + delete_node` 冒充可靠回滚；
- 不对结果未知的写操作自动重放；
- 不为了提高“成功率”把安全拒绝改名为成功；
- 不承诺用户可以任意删除结构房间后自动恢复原场景。

## 12. 内部部署 Gate

在以下条件满足前，增删改功能不应作为“稳定支持”开放给内部多人试用：

- [ ] 所有写工具没有透明自动重试；
- [ ] 零写入失败不会显示部分修改警告；
- [ ] 家具房间和目标绑定不存在首项猜测；
- [ ] 单件增加、删除、替换的标准和自然语言回归全绿；
- [ ] 批量删除要么正式支持并确认，要么在写入前给出准确说明；
- [ ] 混合修改部分失败后 Session 与场景一致；
- [ ] 面积目标按用户语义验证；
- [ ] 能力矩阵不再把条件支持写成无条件支持；
- [ ] deterministic 全量通过；
- [ ] 经授权的 Provider 抽查和浏览器人工验收通过。
