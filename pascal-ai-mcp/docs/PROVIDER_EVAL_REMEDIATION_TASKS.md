## 3. 问题归类

### 3.1 产品代码问题

1. **结构修改存在重复确认。** 删除请求先经过通用删除确认，进入修改执行后又因 `plan_rebuild` 再次要求确认。
2. **确认后重新调用模型解析修改计划。** 用户确认的不是一份稳定计划；第二次模型输出变化会导致 plan hash 不一致、再次确认或无操作。B 阶段曾把“重新翻译并要求 SHA-256 完全一致”视为安全失败策略，真实 Provider 评测证明它虽然不会误执行，却会因模型产生语义相同但字面不同的 operations 而长期停在确认状态，因此本文件的 G2.2 正式取代该设计。
3. **局部修改无法满足时会退化为整体重建。** case-21 已证明这会改变外轮廓和多个无关房间。
4. **缺少操作级后置条件。** 通用 Gate 通过并不代表“新增书房”“扩大主卧”“删除卫生间”等用户目标已实现。
5. **必备设备可放置性不足。** 布局验证通过后仍可能放不下马桶或洗手台。
6. **大户型分区策略过于僵硬。** 面积充足的 case-11/15 仍被比例分宽、角落湿区和走廊约束拒绝。

### 3.2 评测代码问题

1. `modelCallBudget` 会混入 `setupFrom` 的基础户型生成调用，不能准确表示本次修改成本。
2. Case 未显式声明时，碰撞、需求遗漏、挡门和必备设备缺失不一定使结果失败。
3. `unknown` 无法区分“等待第二次确认”“修改安全拒绝”和“执行异常”。
4. 文档口头称 24 个用例，但实际语料库只有 23 个文件。

### 3.3 Provider 波动

本次存在一次可重试 HTTP 错误，重试后成功。它没有造成 Case 失败。当前 10 个失败均有稳定的规划、状态机、修改结果或验证证据，不能简单归因于 Provider 随机性。

此前 case-13/14/19/20/21/23 的确定性测试使用固定模型输出，无法复现“确认前后真实模型输出漂移”，所以测试全绿只证明了固定 operations 下的状态机和执行器行为，没有证明 live model 的确认链路可用。后续回归必须显式覆盖该差异，不能再用同一 fixture 重放两次来代表真实确认。

### 阶段 G2：结构修改只确认一次

依赖：G1.1、G1.3。

#### [x] G2.1 固化确认状态机契约

目标：用确定性测试先描述单次确认流程。

覆盖场景：

- add room；
- remove room；
- resize room；
- chained modification；
- 用户在等待确认时发送新指令；
- 用户取消确认。

完成标准：每项结构修改最多一次确认，确认前零场景写入。

实施记录（2026-07-24）：add/remove/resize 统一先进入修改计划流程；等待确认时的新指令会废弃旧计划，取消会清除计划；确认前不进入 plan-first 施工。确定性测试覆盖结构请求路由、替换和取消。

#### [x] G2.2 持久化规范化修改计划

目标：模型只解析一次；确认时执行用户看到并同意的同一份计划。

设计约束：

- 在 Session 业务态保存规范化 operations、mode、reason 和 canonical hash；
- 不保存模型原始响应；
- 不把 operations 参数值写入审计表；
- checkpoint 只保存恢复引用/session version，不成为第二真相源；
- Session 删除时按现有语义清理待确认计划。

完成标准：

- 确认请求不再调用 `modify-ops` 模型；
- canonical hash 在确认前后保持一致；
- 回归测试让首次计划与“假设中的第二次模型输出”存在字段顺序、别名或数值细节差异，并证明确认路径根本不会消费第二份输出；
- 进程重启后仍可确认同一计划；
- 修改计划变化时旧确认自动失效。

实施记录（2026-07-24）：Session 保存规范化 `pendingModifyPlan`，canonical hash 使用稳定键排序后的 JSON；确认请求直接执行该计划，`modify-ops` 翻译器调用次数为 0。计划随 SQLite Session 持久化，重启后仍可确认；不保存模型原始响应。

#### [x] G2.3 合并删除确认入口

目标：删除请求不再经历“通用删除确认 + plan rebuild 确认”两层流程。

完成标准：

- 删除意图先形成规范化计划，再展示一次最终确认；
- 确认文案明确受影响范围和是否允许整体重排；
- case-19/20 单次 confirm 后到达明确终态；
- 不削弱破坏性写入前的确认要求。

实施记录（2026-07-24）：删除意图不再经过通用删除确认，和其他结构修改一样只展示一次最终 plan-rebuild 确认；确认仍绑定服务端 Session 中的 canonical plan。

#### [x] G2.4 连续修改状态隔离

目标：第二条修改不能覆盖、复用或误确认第一条待确认计划。

完成标准：

- 新消息到达时显式替换或取消旧计划；
- 每轮修改有独立 canonical hash；
- case-23 的两次修改按顺序执行；
- 不产生跨 Session/Scene 污染。

实施记录（2026-07-24）：每条新修改消息先清除旧 pending plan、hash、mode 和确认标志；确认只消费当前 Session 当前计划。连续修改分别生成独立 canonical hash。
